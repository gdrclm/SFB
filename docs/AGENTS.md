Этот репозиторий содержит разработку браузерного рабочего среза игры Speed Fall Ball.

Перед любыми изменениями агент обязан полностью прочитать:

- `docs/GDD.md`
- `docs/MasterPlan.md`
- этот файл `AGENTS.md`

## Приоритет документов

Используй следующий порядок приоритета:

1. Прямое текущее указание пользователя.
2. `docs/GDD.md` — источник требований к игре.
3. `docs/MasterPlan.md` — порядок выполнения работ.
4. `AGENTS.md` — правила работы агента.
5. Существующая реализация проекта.

Если документы противоречат друг другу:

- не придумывай решение;
- не выбирай один из вариантов самостоятельно;
- укажи точные противоречащие разделы;
- останови выполнение спорной части.

## Главный принцип

Выполняй только явно указанную задачу.

Не добавляй новые:

- механики;
- режимы;
- типы платформ;
- валюты;
- улучшения;
- элементы управления;
- визуальные темы;
- способы монетизации;
- системы прогрессии;
- продуктовые требования;
- технические требования, меняющие замысел игры.

Не трактуй собственные предположения как требования проекта.

## Работа по мастер-плану

Разработка выполняется последовательно по этапам из `docs/MasterPlan.md`.

Для каждого запроса:

1. Определи номер текущего этапа.
2. Повторно прочитай соответствующий раздел `docs/MasterPlan.md`.
3. Проверь связанные требования в `docs/GDD.md`.
4. Изучи текущее состояние проекта.
5. Выполни только задачи текущего этапа.
6. Не выполняй будущие этапы заранее.
7. Не меняй уже работающие части без необходимости.
8. Проверь результат по критериям текущего этапа.
9. Остановись после завершения этапа.

Если номер этапа не указан, не начинай разработку всего проекта. Сначала определи по запросу пользователя, какой конкретный этап требуется выполнить.

## Границы первого рабочего среза

Реализуй только функции, включённые в первый рабочий срез согласно GDD и MasterPlan.

Не реализовывай до отдельного прямого указания:

- рекламу;
- реальные платежи;
- покупку полной версии;
- кристаллы;
- магазин;
- платные скины;
- ежедневные бонусы;
- семидневный streak;
- еженедельные задания;
- процедурные квесты;
- сервер;
- лидерборды;
- создание платформ игроком;
- движущиеся платформы;
- дополнительные механики;
- полноценную систему достижений.

## Технологический стек

Не выбирай и не меняй технологический стек самостоятельно.

Для этого проекта зафиксирован следующий обязательный web-native стек:

- Babylon.js 9;
- TypeScript в строгом режиме;
- Vite;
- ESLint;
- Vitest;
- Babylon Physics V2 с Havok Physics;
- Blender и GLB / glTF 2.0;
- Babylon Node Material и собственный `ToonSketchMaterial`;
- Babylon Outline Renderer и Custom PostProcess;
- GlowLayer, Bloom и GPU Particles;
- Blender animations, Morph Targets и Babylon Animation;
- HTML + CSS поверх Canvas;
- WebGL2 как основной режим рендера;
- WebGPU как дополнительный режим.

Проект не использует Unity, C#, URP или Unity WebGL Build. Запрещено создавать Unity-проект, C#-файлы, Unity assets, `Packages`, `ProjectSettings` или другие элементы Unity-структуры.

Используй только:

- стек, явно указанный пользователем;
- зафиксированный выше стек;
- совместимую с ним структуру, уже существующую в репозитории;
- технические решения, прямо зафиксированные в GDD или MasterPlan.

Если стек ещё не определён и проект пустой:

- не создавай проект на случайно выбранном движке;
- не добавляй зависимости;
- не выбирай язык программирования;
- сообщи, что стек не зафиксирован.

## Допустимые технические решения

Если для выполнения текущего требования не хватает низкоуровневой технической детали, выбери минимальную реализацию, которая:

- выполняет только текущее требование;
- не меняет игровой дизайн;
- не создаёт новую механику;
- не расширяет объём проекта;
- не мешает следующим этапам;
- может быть заменена без переработки всей системы.

Не превращай техническое решение в новое продуктовое требование.

## Работа с существующим кодом

Перед изменением файлов:

1. Найди связанные системы и зависимости.
2. Проверь, что уже реализовано.
3. Не создавай дублирующие системы.
4. Не переписывай рабочий код без необходимости.
5. Сохраняй текущую структуру проекта, если она не мешает задаче.
6. Делай минимальный набор изменений.
7. Не выполняй массовый рефакторинг в рамках функционального этапа.

Если рефакторинг необходим, он должен быть ограничен текущей задачей.

## Изменение документов

Не изменяй:

- `docs/GDD.md`;
- `docs/MasterPlan.md`;
- `AGENTS.md`;

если пользователь прямо не попросил изменить конкретный документ.

Не исправляй требования молча.

## Проверки

После каждой реализации:

1. Запусти доступные автоматические проверки.
2. Проверь ошибки сборки.
3. Проверь ошибки выполнения.
4. Проверь, что ранее реализованные функции не сломаны.
5. Сравни результат со всеми пунктами текущего этапа.
6. Исправь проблемы текущего этапа.
7. Не скрывай непроверенные части.

Не заявляй, что этап завершён, если:

- часть требований не реализована;
- сборка не проходит;
- остаются известные ошибки;
- результат не был проверен;
- использованы временные заглушки вместо требуемого поведения.

## Временные заглушки

Не оставляй заглушки без явного обозначения.

Если полноценное выполнение невозможно из-за отсутствующего ресурса:

- реализуй только минимально проверяемую часть;
- явно укажи ограничение;
- не выдавай заглушку за готовую функцию;
- не добавляй вымышленные ресурсы или требования.

## Формат отчёта после работы

После выполнения задачи сообщи:

### Выполнено

- какие требования реализованы;
- какой этап выполнен;
- какие пункты этапа закрыты.

### Изменённые файлы

- список созданных файлов;
- список изменённых файлов;
- краткое назначение каждого изменения.

### Проверки

- какие команды или проверки были запущены;
- что прошло успешно;
- что не удалось проверить.

### Ограничения

- известные ошибки;
- незавершённые пункты;
- внешние зависимости;
- необходимые ручные проверки.

### Статус

Используй один из вариантов:

- `ЭТАП ЗАВЕРШЁН`
- `ЭТАП НЕ ЗАВЕРШЁН`

Не начинай следующий этап после отчёта.

## Запрещённое поведение

Запрещено:

- реализовывать весь MasterPlan одним изменением;
- добавлять функции «на будущее»;
- расширять требования для улучшения проекта;
- выбирать новые технологии без указания;
- менять игровые числа без требования;
- подменять описанные механики более привычными;
- удалять требования, которые кажутся лишними;
- менять правила игры ради упрощения реализации;
- скрывать ошибки или неполную реализацию;
- считать отсутствие ошибки доказательством правильной работы;
- переходить к следующему этапу без указания пользователя.

## Правило остановки

Останови выполнение и сообщи о проблеме, если:

- GDD и MasterPlan содержат прямое противоречие;
- для задачи требуется выбор незафиксированного технологического стека;
- запрос требует добавить отсутствующую в документах игровую механику;
- невозможно проверить результат;
- отсутствует необходимый файл или ресурс;
- задача выходит за границы указанного этапа.

Не останавливай работу из-за мелких технических решений, которые можно принять минимальным способом без изменения требований.

## Критерий качества

Хороший результат:

- строго соответствует текущему запросу;
- соответствует GDD;
- следует MasterPlan;
- не содержит самодеятельности;
- не выполняет будущие этапы;
- минимально изменяет проект;
- проверен;
- честно описывает ограничения.
