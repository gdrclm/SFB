# Сетевое демо SFB

Сетевая часть — анонимный аккаунт, имя и общий рейтинг. Игроки не управляют шарами друг друга. Во время падения нет сетевых запросов; сервер нужен при входе, старте/завершении рейтинговой попытки и открытии таблицы.

## Что уже реализовано

- Анонимный ID и имя 2–16 символов; повторный вход в том же браузере восстанавливает аккаунт.
- Рейтинговое демо: 120 секунд активной игры или поражение, без купленных улучшений. Косметика сохраняется. Свободный/обучающий забег остаётся локальным.
- Добровольный выход/перезапуск не публикует незаконченную попытку.
- Один лучший результат на `(player_id, demo_version)`, серверный пересчёт очков. При равенстве — глубина, максимальная скорость, более ранний результат и ID.
- Общий TOP 20 и собственное место вне TOP 20. Обновление при открытии, после отправки/возврата сети и каждые 10 секунд, пока окно открыто. WebSocket не нужен.
- Локальное сохранение предшествует отправке. Очередь до 20 попыток хранится отдельно, сохраняет самые высокие результаты, повторяет отправку при восстановлении сети/через 30 секунд. Чужой аккаунт не отправляет эту очередь.
- Сброс локального прогресса сохраняет сетевую сессию и очередь. Полная очистка данных браузера теряет доступ к анонимному аккаунту. Публичный ID не является ключом входа.

## Временный сервер без Supabase

Node.js **24** и SQLite из стандартной библиотеки, без дополнительных серверных зависимостей:

```sh
npm run server
```

API слушает `127.0.0.1:8787`. База `.runtime/ratings.sqlite` и её WAL-файлы не попадают в Git. Токены выдаются сервером, в базе хранятся только SHA-256 хеши. Запросы аутентифицируются Bearer-токеном; подставить чужой `player_id` в результате нельзя.

Для локальной игры создайте `.env.development.local`:

```env
VITE_TEMPORARY_API_URL=http://127.0.0.1:8787
```

Затем `npm run dev`. У двух браузеров будут разные ID и общий настоящий рейтинг. Локальный адрес доступен только на машине, где работает сервер: его **нельзя** указывать для игроков GitHub Pages.

### Публикация бесплатного временного API

В репозитории есть `render.yaml` для Render Blueprint:

[Развернуть временный сервер на Render](https://render.com/deploy?repo=https://github.com/gdrclm/SFB)

1. Подключить репозиторий и развернуть Blueprint. Нужна учётная запись Render.
2. Получить HTTPS-адрес сервиса, проверить `https://АДРЕС/health`.
3. В `public/network-config.json` указать `temporaryApiUrl: "https://АДРЕС"`. Остальные адреса/ключи оставить пустыми.
4. Запустить `npm run build` и обновить `docs/` в репозитории. При ручной проверке готовой Pages-сборки можно также менять `docs/network-config.json`; исходником для следующей сборки остаётся файл в `public/`.

Сборка Pages читает JSON при запуске: серверный адрес не требует переписывания игры. Перед публикацией проверить, что в `docs/network-config.json` нет `localhost`/`127.0.0.1`. Переменная `VITE_TEMPORARY_API_URL` также поддерживается, но встраивается на этапе сборки и имеет приоритет над JSON.

На внешнем хосте слушатель использует `PORT` и `HOST=0.0.0.0`. Допустимые браузерные источники задаёт `SFB_ALLOWED_ORIGINS` (через запятую). Для Pages проекта — `https://gdrclm.github.io`, без `/SFB/`.

**Временный означает недолговечный:** бесплатный Render может засыпать и теряет SQLite при пересоздании/деплое контейнера. Для устойчивого рейтинга нужен постоянный диск/резервная копия либо Supabase. Файл SQLite сам по себе сохраняется при обычном перезапуске процесса на постоянном диске. Сервер в облачной рабочей среде также живёт только вместе с этой средой.

В этой сессии API проверен локально. Публичный Cloudflare Quick Tunnel запустить не удалось из-за DNS/сетевых ограничений среды, включая повтор с расширенным доступом. Неработающий адрес не добавлялся в Pages.

## Подключение Supabase позже

Клиент поддерживает второй адаптер с теми же операциями; Babylon и игровой цикл менять не требуется.

1. Создать проект Supabase, включить Authentication → Anonymous Sign-Ins.
2. Выполнить `supabase/migrations/202610210001_demo_leaderboard.sql` в SQL Editor или применить через CLI.
3. В `public/network-config.json` очистить `temporaryApiUrl`, заполнить HTTPS `supabaseUrl` и публичный `supabasePublishableKey` (publishable или прежний anon JWT). Service-role/secret ключи не использовать.
4. Собрать и опубликовать `docs/`.

Supabase SDK загружается динамически только при выборе этого адаптера. Права таблиц закрыты через RLS и revoke; изменения проходят через RPC с `auth.uid()`, проверкой владельца попытки и атомарной записью лучшего результата. Анонимный пользователь Supabase получает роль `authenticated` — это не публичная роль `anon`.

У двух провайдеров разные системы аккаунтов. При переходе Supabase создаст новую анонимную сессию; перенос временных тестовых ID/результатов требует отдельной миграции данных, если они нужны.

## Версия демо и проверки

Текущая версия: `demo-2026-10-21`. При изменении баланса заведите новую версию и на клиенте, и в серверной таблице `versions` / `sfb_demo_versions`. Рекорды разных версий не смешиваются. Один UUID попытки принимается один раз, повторные запросы идемпотентны; время начала выдаёт сервер.

Сервер проверяет диапазоны, время, серию и связь глубины с максимальной скоростью; очки считает как `depth + coins*10 + platforms*25 + combo_bonus`. Это базовая проверка демо, **не полноценный античит**: браузер может подделать согласованный набор показателей. Для соревнований с призами нужна проверка воспроизведения действий/серверная симуляция. Имена и результаты публичны; IP не сохраняются в базе, используются временные ограничения частоты запросов.

Проверки:

```sh
npm test
npm run test:server
npm run lint
```

`supabase/tests/leaderboard.sql` проверяет RPC, RLS, владельца попытки, повторную отправку, лучший результат и имена в отдельной тестовой базе. Это тест с rollback, но его нужно запускать только в тестовом проекте с тестовыми пользователями.
